# Работа с вопросами в WB OPS

## Быстрый процесс добавления индивидуальных ответов

Для обычного добавления сценариев в режим «Индивидуальные» используй один цикл без широкого исследования репозитория:

1. Перед началом проверь `git status --short`, `git log --oneline origin/main..HEAD` и remote. Если `main` содержит посторонние неопубликованные коммиты, готовь чистую ветку от `origin/main`; не отправляй весь `main`.
2. Рабочая область по умолчанию: `app/services/question_composer.py` и `test_question_replies.py`. Другие файлы подключай только после обнаружения конкретной зависимости. Не открывай секреты и `.env`.
3. Для каждого нового вопроса добавь распознавание смысла и адресный тест: данные покупателя и товара, ожидаемый ответ и отсутствие выдуманных размеров, характеристик или наличия. Если нужны факты товара, используй существующие данные модели.
4. Единственная обязательная локальная проверка: `.venv/Scripts/python.exe -m pytest -q test_question_replies.py` и `git diff --check`. Успешный прогон не повторяй без признаков ошибки.
5. Не меняй `app/knowledge/questions.json` при обычном добавлении дефолтного сценария: это справочник исторических вопросов и ответов для точных совпадений. Не переписывай его при выкладке.
6. Коммит должен содержать только профильные файлы. При чистом `main` отправляй его; при посторонних локальных коммитах публикуй изолированную ветку от `origin/main` с одним тематическим коммитом.
7. После успешного Git создай один атомарный релиз из текущего серверного, замени только относящиеся файлы, сохрани постоянные данные и `app/knowledge`, перезапусти только `wb-ops`.
8. Один раз проверь `systemctl is-active wb-ops`, оба health endpoint и совпадение хеша изменённого runtime-файла. При успехе не выполняй дополнительные повторные проверки.

Целевой отчёт: максимум 6 строк — сценарии, тесты, Git-коммит/ветка, серверный релиз, health, риски.
